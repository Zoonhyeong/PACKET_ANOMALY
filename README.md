# PACKET_ANOMALY — PCAP 기반 네트워크 이상 트래픽 탐지·분석 도구

pcap/pcapng 파일을 올리면 플로우 단위로 이상 트래픽을 찾고, **왜 이상한지(규칙 근거 + 모델 원인 특징)** 와
**MITRE ATT&CK 기법**을 함께 보여주는 관제 보조 도구입니다.

```
pcap ─▶ 패킷 파싱(dpkt) ─▶ 양방향 플로우 집계 ─▶ 특징 39개 ─▶ Isolation Forest ─┐
                                    │                                        ├─▶ 위험도 정렬 + 설명 + ATT&CK ─▶ 웹 대시보드
                                    └──────▶ 규칙 엔진(출발지 행위 맥락) ──────┘
```

## 주요 기능

| 단계 | 내용 |
|---|---|
| 패킷 파싱 | dpkt 로 pcap/pcapng 파싱, IPv4/IPv6, 이더넷·SLL·loopback 링크 지원. 길이는 IP 헤더 값 사용(페이로드 잘린 캡처도 정확) |
| 플로우 집계 | 양방향 5-tuple, idle timeout 60초 / RST / 양방향 FIN 으로 종료. 연결 시작 쪽을 정방향으로 |
| 특징 | 패킷 수·바이트·길이 통계, 패킷 간격(IAT), 초당 전송량, TCP 플래그 수, TTL, 윈도우 + 내부/외부, 프로토콜, 포트 범주 |
| 탐지 모델 | Isolation Forest. **기준선 모드**(정상 트래픽으로 학습해 저장, 목표 오탐률로 임계값) / 캡처별 모드 |
| 규칙 엔진 | 출발지별 맥락: 서비스 스캔, 응답 없는 SYN, Brute Force, 반복 연결 DoS, 백도어 포트, 대용량 업로드, 비정상 프로토콜, TTL 이상 |
| 설명 | 특징을 하나씩 정상값(중앙값)으로 바꿨을 때 점수 하락폭 = 모델이 본 원인 Top 3 |
| ATT&CK | 의심 유형을 T1046, T1110, T1498/T1499, T1048, T1071, T1095, T1190, T1571 로 매핑 |
| 웹 | FastAPI 비동기 작업(진행률 표시) + React 대시보드(점수 분포, 상위 플로우, 이상 플로우 상세) |

## 실행

```bash
# 백엔드
cd backend && python -m venv .venv && .venv/bin/pip install -r requirements.txt
.venv/bin/uvicorn main:app --reload

# (선택) 정상 트래픽으로 기준선 모델 학습 -> backend/models/baseline.joblib
.venv/bin/python packet_analysis.py --fit-baseline normal1.pcap normal2.pcap --target-fpr 0.01

# 프론트엔드
cd frontend && npm install && npm run dev
```

기준선 모델이 없으면 캡처마다 새로 학습하는 모드(상위 2%를 이상으로 판정)로 동작합니다.

## 성능 평가 (CTU-13 공개 데이터셋)

```bash
eval/download_ctu13.sh                         # 약 1.6GB
backend/.venv/bin/python eval/evaluate_ctu13.py  # 결과: eval/results/ctu13_results.md
```

**데이터**: [CTU-13](https://www.stratosphereips.org/datasets-ctu13) (체코 공대 Stratosphere Lab, 실제 대학 네트워크 + 봇넷 감염 호스트)

| 용도 | 시나리오 | 봇넷 | 플로우 수 |
|---|---|---|---:|
| 기준선 학습 + 규칙 진단(dev) | s48 | Sogou | 161,369 |
| 테스트 | s46 | Virut (IRC C2, 스팸, 연결 시도) | 179,495 |
| 테스트 | s52 | Rbot 3대 (IRC C2, ICMP DDoS) | 126,497 |

- 기준선 모델은 s48에서 Botnet 라벨을 뺀 트래픽으로만 학습하고, 테스트 시나리오는 학습에 쓰지 않았습니다(다른 날 캡처).
- 정확도는 **Botnet(양성) vs Normal(음성)** 만으로 계산했습니다. Background 는 데이터셋에서도 미확인 트래픽이라 정답으로 쓰지 않고, 경보 수(관제 업무량)에만 포함했습니다.

### 개선 과정에서 확인한 것

1. **규칙 오탐 원인 분석과 수정**
   첫 평가에서 규칙 엔진의 정상 트래픽 오탐률이 **56.3%(s46) / 45.2%(s52)** 였습니다.
   학습용 s48 로 원인을 분석해 보니 오탐 전부가 "반복 연결 = DoS" 규칙이었고, 내부 DNS 서버로 가는 질의(UDP 53)와 프록시로 가는 HTTP 가
   대부분이었습니다. 연결이 많아도 정상 응답을 받으면 DoS 가 아니므로, **반복 연결 중 실패(응답 없음/RST) 비율이 50% 이상**일 때만
   DoS 로 판정하도록 바꿨습니다.
   → 정상 오탐률 **56.3% → 0.9% (s46), 45.2% → 1.8% (s52)**, s48 은 43.9% → 0%. 전체 경보는 71,511 → 31,922건(s46).

2. **기준선 모델로 오탐률 제어**
   캡처별 학습은 깨끗한 트래픽에서도 항상 상위 2%를 이상으로 뽑습니다. 기준선 모델은 임계값을 "정상 트래픽에서 오탐률 1%"로 정하는데,
   학습에 쓰지 않은 다른 날 트래픽에서 **실측 FPR 1.0% / 0.6%** 로 목표가 유지됐습니다.

3. **모델 단독의 한계**
   Isolation Forest 는 봇넷 C2 를 거의 잡지 못했습니다(Recall 0.4~9%). C2 는 일반 HTTP/HTTPS 와 플로우 통계가 비슷하고,
   대학 네트워크에는 실패한 연결 시도 같은 "드문 트래픽"이 원래 많기 때문입니다. 반면 출발지 행위 맥락을 보는 규칙은
   감염 호스트의 연결 시도(TCP-Attempt)를 96% 탐지했습니다.

4. **하이브리드 = 우선 확인할 경보**
   모델과 규칙이 모두 이상으로 본 경보(D)는 Precision 100%, 경보 호스트 수를 1,080개(A) → 9개로 줄이면서 감염 호스트를 3위 안에 올렸습니다.
   Recall 이 낮아 단독 탐지 수단이 아니라 **분석가가 먼저 볼 고신뢰 경보 등급**으로 쓰는 것이 맞습니다.

### 한계와 다음 단계

- 플로우 단위 Recall 이 낮음. 호스트 단위 시계열 특징(주기성·접속 대상 다양성)으로 C2 비컨 탐지를 보강할 필요
- 평가 데이터가 2011년 대학 네트워크 3개 시나리오로 제한적. CIC-IDS2017(등록 후 다운로드) 등으로 확장 예정
- Suricata(ET Open 룰) 결과와 비교, 결과를 JSON 로그로 내보내 SIEM 연동

## 구조

```
backend/
  main.py             FastAPI (POST /analyze -> job_id, GET /jobs/{id})
  packet_analysis.py  pcap -> 패킷 -> 플로우 -> 특징 -> Isolation Forest, 기준선 모델 학습/저장
  packet_anomaly.py   규칙 판정, 출발지 맥락 위험도, 모델 원인 설명, ATT&CK 매핑
frontend/             React + Vite 대시보드
eval/
  download_ctu13.sh   평가 데이터 다운로드
  evaluate_ctu13.py   평가 스크립트
  results/            평가 결과 (md, json)
```
